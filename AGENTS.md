# mslam

C++20 LiDAR/IMU SLAM (Eigen, jsoncpp, gRPC). Entrypoint `src/main.cc`; libs in `src/{slam,map,config}`; proto in `grpc/slam.proto`; architecture notes in `docs/arch.md`.

Layering: `Slam` (estimator, no I/O) <- `SlamPipeline` (per-scan sequence, publishes to an `ISlamOutput`) <- `SlamRunner` (live loop over `SensorInput`, `ISlamControl`). `SlamServer` is the gRPC `ISlamOutput`; `src/main.cc` wires them and owns the signal handlers.

## Build & test
- Build and parallelism: plain C++ built by GCC (`gcc` preset, GCC 16 in the repo's image, and `pi5`). oneTBB is the parallel path (details below, "Threads"; CMake option `MSLAM_WITH_TBB`, default ON, `find_package(TBB QUIET)` before moptim's subdirectory, which also gets `MOPTIM_WITH_TBB` from it). The compute path is the CPU code: `VoxelHashMap` with the `CorrespondenceFinder` search and `NormalEstimator::estimateAll` (parallel on a `ParallelExecutor` when `num_threads` != 1, otherwise the original loops), `Preprocessor` with `deskewInto()` and `VoxelFilter`, and `moptim::LevenbergMarquardt` on the fused costs. `Slam` and `ScanSequenceRegistration` create one `moptim::ExecutionContext` for their costs (`setThreads(num_threads)`, so one knob per program; moptim goes wide only for large costs, from 6 partitions per linear system or 12 per cost-only evaluation, so mainly the big `register_scans` clouds, while the per-scan SLAM costs are one partition and run inline; results stay bit-identical at any thread count) next to the executor and hand both to the registrations (`IcpWorkspace`). `-DMSLAM_MOPTIM_SOURCE_DIR=<dir>` builds against another moptim tree than the submodule (e.g. the devcontainer's `/moptim` bind mount, or `/workspaces/moptim`). Compare builds and thread counts with `test/bench_threads.py` (readme, "Comparing thread counts and builds"): interleaved runs, minima, pose distances, and exit status 1 if a pose changes between rounds or thread counts. The registrations keep their moptim costs and optimizer from one round and scan to the next (`Solver` in `ImuRegistration.cc` / `PointToPlaneRegistration.cc`: `setData()`/`setModel()` each round), the IMU registration fuses the point-to-plane cost and the IMU factor into one `moptim::FusedCost`, and speculative linear systems are on (`MOPTIM_SPECULATIVE=0` turns them off for a comparison; `IcpWorkspace.cc`); all three are bitwise neutral. `ImuPreintegrationFactor` holds a `PreintegratedImu` copy and calls the inline `preintegrationResidual()` (`ImuPreintegration.hh`), and has an analytical jacobian (`jacobian()`, the derivation in its comment; `AnalyticalJacobianMatchesCentralDifferences` checks it against central differences to 1e-6) used through `moptim::AnalyticalCost`: one residual and jacobian per linear system instead of 49 residuals. `normalFromPoints()` (`NormalMath.hh`) and `rotationIncrement`/`RotationIncrementMemo` (`DeskewMath.hh`) are the shared inline math of the normals and the deskew. `se3Plus()` (`SE3Manifold.hh`) is the manifold's step. `SlamServer.cc`, `Conversion.cc` and `PointCloudIO.cc` form `slam_io` (gRPC/protobuf), which does not link moptim: link `slam_io` where they are used.

- Tests are GTest in `test/` (`test_slam`, `test_preprocessor`, `test/map`): run `ctest --test-dir build/gcc`, or a single binary with `--gtest_filter=...`.
- Integration tests replay recordings through the full pipeline from `test/integration/` (skipped if the untracked recording is absent). The test replays `living_room_garden` in-process: synchronously through `SlamPipeline` (as `bench_slam` does), synchronously again with `slam.num_threads` 4 (its pose must equal the first bit for bit, `FourThreadsMatchTheSynchronousReplay`; skipped in a build without oneTBB), and through the live loop, with a `msensor::RecordingSensorDriver` handed to `SlamRunner::run` (no gRPC replay server or remote client). The live run is deterministic: `SlamRunnerOptions` selects `SensorOverflow::Block` (the sensor input holds the playback thread back instead of dropping) and a 30 s IMU wait, the playback is unpaced, and the run starts when the loop has registered its callbacks and stops when every emitted scan was processed, so nothing depends on the wall clock. It asserts no dropped scan, no IMU-wait timeout, and a final pose equal to the synchronous replay bit for bit (so also equal to `bench_slam`'s), besides the 0.1 m gate. If the live pose ever differs from the synchronous one, the live loop paired or ordered the data differently: that is a bug, not noise. The whole binary is one CTest entry (`SlamIntegration`, about 8 s with the 4-thread replay), because its four tests share the replays. It is not a benchmark. They are opt-in: default `cmake`/`ctest` never build or run them. Enable with `cmake --preset gcc -DMSLAM_INTEGRATION_TESTS=ON`, then `ctest --test-dir build/gcc -L integration`. Or run directly with `cmake --build --preset build-gcc --target integration-test`.
- `bench_slam` (`test/bench_slam.cc`) is the deterministic replay benchmark (built by default): `cmake --build --preset build-gcc --target bench_slam`, then `build/gcc/test/bench_slam test/integration/mslam.jsonc test/data/<recording>.pbscan [repeats]`. It reads the recording synchronously through `SlamPipeline` (the same code the live loop runs), prints the scan count, total and per-stage times and the final pose (9 digits), then the register stage split (`register split: search= normals= assembly= solve= other=` ms, summed over both registrations; benchmark-only env knob: `MOPTIM_SPECULATIVE=0` turns speculative linear systems off), then the registration statistics (IMU-path vs LiDAR-only scans, mean first-round correction) and the IMU/scan synchronisation counters, and is not registered with CTest. `--threads <n>` overrides `slam.num_threads` (see "Threads" below); the pose must not change with it. `--imu-fusion <preintegration_factor|dead_reckoning>` overrides `slam.imu_fusion` of the config (the `registration:` line then shows `dead_reckoning=<n>` instead of `imu_path`). `--trajectory <out.csv>` writes one row per registered scan (timestamp, pose, velocity, biases, first-round correction in mm and mrad; last run only). `uv run test/plot_imu_fusion.py A.csv B.csv out.png` plots a mode A and a mode B trajectory file against each other. `--save-map <file.ply>` (anywhere on the command line) also writes the final accumulated map, i.e. all published map increments concatenated as `SlamServer::GetMap` serves them (not the bounded `VoxelHashMap`), as a binary PLY (`writePlyPointCloud`, readable by `viewer/`); with `repeats` > 1 it is the last run's map, and an unwritable path fails before the run. It pairs IMU samples with scans by timestamp (`SlamPipeline::pushImu` / `processSyncedScan`), like the live loop; see "Time convention" in `docs/arch.md`. For a refactor that must not change results the pose must match to the last digit; compare timings as minima over interleaved runs (the host is noisy).

- Threads (oneTBB; the study, with the measurements, is kept in `improvement_tbb.md`): `slam.num_threads` (optional, integer 0..256, default 1), `registration.num_threads` for `register_scans`, and `bench_slam --threads` set how many threads run the 1-NN correspondence search and the normal estimation of uncached map points (1 = the original sequential loops, 0 = every hardware thread, n = at most n, caller included). Both go through one `ParallelExecutor` (`include/mslam/utils/Parallel.hh`, a bounded `tbb::task_arena` with a `static_partitioner`, inline when n < 2 x grain; TBB headers only in `src/utils/Parallel.cc`) that `Slam` / `ScanSequenceRegistration` create (`makeParallelExecutor`, declared before the registrations that use it) and pass to the registrations and finders; the same number sets `moptim::ExecutionContext::setThreads()` of the context they hand to the costs. The result is bit-identical at any thread count: a parallel body writes only its own index's slot, and compaction, normal-cache insertion and constraint assembly stay sequential in the original order. Keep that rule for any new parallel code; if a pose differs between thread counts it is a bug, not noise (`FourThreadsMatchTheSynchronousReplay`, `ParallelCorrespondenceFinder.*`, `ParallelAlignMatchesSequentialBitForBit`). `IMap::getClosestNeighbor` / `findClosestNeighbors` must stay safe for concurrent readers (contract in `IMap.hh`). Build: CMake option `MSLAM_WITH_TBB` (default ON); without oneTBB the build is sequential and `num_threads` != 1 logs a warning (`libtbb-dev` to build, `libtbb12` in the deployment image). Config errors: `slam.backend` and a top-level `sycl` block (the removed SYCL settings) are rejected with an error naming `slam.num_threads`, `registration.num_threads` for the registration config. Measured 2026-11-16 in the dev container (M3 Pro host, 5 performance cores): `living_room_garden` register 1569 ms -> 670 ms at 4 threads (total 1946 -> 1050 ms), slower again at 6 to 8 threads; `register_scans` on the reference clouds 2.32 s -> 0.64 s at 8 threads. - `Point3PlaneDistance` is scalar code on AVX+FMA builds (2026-11-25, `PointDistance.hh`): the Eigen expressions compile with `-mavx` to `vmaskmovpd` masked loads/stores for the size-3 vectors, which cannot be store-forwarded, so the residual and jacobian cost 10.9 + 25.7 ns per element (the SSE-only build of the same code needs 2.6 times less). The scalar version keeps the exact operation order of that machine code (explicit `std::fma` where it was fused, `opaque()` to keep the plain products from being contracted), so it is **bit-identical**: `bench_slam` final poses equal the pre-change ones to all 9 digits on `living_room_garden` and `rooms` at `--threads` 1 and 8, and `test_point_distance` checks it against the Eigen expressions with `EXPECT_EQ`. Measured on the x86-64 dev container (i7-13850HX, GCC 16, `-march=native`, `--threads 8`, `living_room_garden`, minima of 5): solve 675 -> 271 ms, register 1445 -> 1023 ms, total 2077 -> 1656 ms (with moptim's `AnalyticalJacobian` scatter specialised on the observation dim, 2026-11-25, which alone changed the solve by about 10 ms, within the noise, with the Eigen model, and by 96 ms with the scalar one). Other targets (SSE-only x86, aarch64/NEON) keep the Eigen code and their rounding; the Pi 5 gain, if any, is **unmeasured**. `Point3Distance` has the same stall (23.9 ns for residual + jacobian with AVX, 7.7 ns without, micro-benchmark 2026-11-25) and was left alone; the operation order of a rewrite would have to be read from its assembly the same way.

The pipeline owns a `PoseGraphBackend` only in this mode; odometry runs no new code and its references above are unchanged (checked 2026-11-20: `bench_slam` poses of both recordings to the last digit). Files: `include/mslam/slam/posegraph/` and `src/slam/posegraph/` (`PoseGraph`, `PoseGraphOptimizer`, `KeyframeBuilder`, `LoopCloser`, `PoseGraphBackend`); tests `test_pose_graph_optimizer`, `test_pose_graph_keyframes`, `test_pose_graph_backend`, the pose-graph cases of `test_slam_pipeline`, `test_json_config` and `test_slam_server` (`StreamKeyframes`, `StatusReportsThePoseGraph`). Rules to keep: the front end stays in the odom frame and `T_map_odom` is applied on the output side only; `ISlamOutput` is called from the SLAM thread only (the worker publishes an immutable result the pipeline reads between scans); no result may depend on timing (`synchronous` for replays); the optimizer uses LEFT increments `T <- se3Exp(d) * T` and `[rho, omega]` order (a right-increment Jacobian is silently wrong); `ISlamOutput::clearMap()` (map only, keyframes stay) is what the pipeline calls to re-send the map, `reset()` clears both; the keyframe stream has its own epoch, bumped only by `reset()`.

- `register_scans2d` is `EXCLUDE_FROM_ALL`; build it explicitly with `--target register_scans2d`.
- `register_scans` (`src/register_scans.cc`, built by default, not installed) registers whole clouds point-to-plane, in command-line order: `build/gcc/register_scans [-c registration.jsonc] [--poses poses.jsonc] [-o merged.ply] [--save-poses out.jsonc] a.ply b.pbscan ...` (build: `--target register_scans`; usage in the readme). It only drives existing code through `ScanSequenceRegistration` (`src/slam/`: `VoxelFilter` thinning, `PointToPlaneRegistration`, a `VoxelHashMap` target, a second `IcpWorkspace` for the matched count / RMS), and config parsing lives in `RegistrationConfig` (`src/config/`, `config/registration.jsonc`; unknown keys and bad values throw). Poses file: flat JSON object, key = input file name (or the argument as typed), value `[x y z roll pitch yaw]` (m, rad, `R = Rx*Ry*Rz`) = pose of that cloud's frame in the common frame; `--save-poses` writes the same format. Facts to keep in mind: the map accumulates (cloud i is registered against clouds 0..i-1, never cleared); cloud 0 is not registered; each step starts from the previous estimate unless `--poses` lists the cloud; the map's search radius is `ceil(max_correspondence_distance / map.resolution)` voxels clamped to 1..8 (the SLAM uses one voxel, which would cut a 0.3 m gate to about 0.1 m); a `.pbscan` argument is concatenated raw (no deskew, no SLAM), so it must be a static recording (the two recordings in `test/data/` are moving); a step with no correspondences keeps its prior and the exit code is 2. Tests: `test_scan_sequence_registration`, `test_registration_config`, and the pbscan cases of `test_point_cloud_io`. Measured 2026-11-16 in the dev container with the default config, on clouds cut from a `bench_slam --save-map` map of `living_room_garden` (163616 points; the two halves and a third are disjoint or overlapping subsets of the same points, moved by a known transform, so this checks the tool, not accuracy on independently captured scans): a cloud displaced by 0.10 / -0.06 / 0.04 m and 0.01 / -0.015 / 0.03 rad is recovered within 0.7 mm and 0.13 mrad, 100% matched, RMS 21 mm (the map's own noise), 24 of the 30 rounds (the small-delta early exit does fire here), 1.5 s. A cloud whose prior is 1.4 m / 0.47 rad off converges to a wrong pose and the tool still exits 0: 32% matched and 110 mm RMS are the only sign, so read those two figures. The same cloud with a measured pose 5 cm / 0.02 rad off is recovered within 0.4 mm / 0.07 mrad in 16 rounds, and feeding `--save-poses` back as `--poses` gives a first-round correction below 0.01 mm. `living_room_garden.pbscan` as an argument loads 10838400 points (1447409 after thinning) and takes 86 s; its pose means nothing because the recording moves. No static `.pbscan` exists, so registering a recording is only covered by the synthetic unit tests. A pitfall the tests ran into: with no robust loss, two clouds that share only one surface but have other surfaces within the gate of each other (two walls meeting at a corner) drag those surfaces together round after round; give such a cloud a measured pose and a smaller `max_correspondence_distance`. The clouds of that measurement are kept in `test/data/registration/` (`a.ply`, `b.ply`, `c.ply`, plain PLY, not LFS; `poses.jsonc` holds c's starting pose and lists the true poses in its comments): `build/gcc/register_scans -c config/registration.jsonc --poses test/data/registration/poses.jsonc test/data/registration/{a,b,c}.ply` must print b at `0.099908569 -0.060199187 0.040658667 0.009875589 -0.014945448 0.029959427` and c at `1.499873182 -0.800181006 0.200337936 -0.000066134 0.000016581 0.499981177`; drop `--poses` to see c converge to a wrong pose.
- The replay server lives in `third_party/msensor` (`playback_publisher`); build it with `--target replay-server` (or `playback_publisher`). It is placed next to `mslam` in `build/gcc/`. Install it with `-DMSLAM_INSTALL_REPLAY_SERVER=ON` (off by default, so deployment images omit it).
- The recorder `remote_recorder -a <host:port> [-o out.pbscan]` (msensor) is wired the same way: `--target remote-recorder` (or `remote_recorder`), placed in `build/gcc/`, installed with `-DMSLAM_INSTALL_REMOTE_RECORDER=ON` (off by default; the `gcc` preset turns both on, `pi5` neither). Both tools are wired in `cmake/msensor_tools.cmake` (options and `mslam_msensor_tool()`; the top-level `CMakeLists.txt` includes it before `add_subdirectory(third_party/msensor)` and calls `mslam_add_msensor_tools()` after it); add another msensor executable there with one `mslam_msensor_tool(<executable> <build-target> <install-option>)` line.
- CPU target is set globally via `MSLAM_CPU` (default `native`; the `pi5` preset and `deployment/Dockerfile` use `cortex-a76`). It must be global for Eigen ABI consistency across TUs; don't remove or apply per-target. The `gcc` preset's toolchain adds `-march=armv8-a`, which overrides `-mcpu`'s ISA, so use `pi5` for Pi deployments.

## Running
- The sensor source is chosen by `remote_scanner` in the config: `"local"` uses the on-board Mid360, any other value is a `host:port` of a sensor server.
- Replay a recording as a separate sensor server, then point `mslam` at it:
  `build/gcc/playback_publisher -f <file>.pbscan [-s <speed>] [-p <port>] [--autoplay]` (`speed` 1.0 = real time, 0 = max; default port 50051), and in another terminal `build/gcc/mslam -c config/mslam.jsonc` with `remote_scanner` set to the server. The recordings are in `test/data/` (see "Recordings and correctness gates").
- In remote mode `src/main.cc` requests an IMU queue of 1000 (= `k_max_queued_imus` in `SensorInput.cc`) and a scan queue of 1 (= `k_max_queued_scans`) through `msensor::RemoteClientOptions`; keep them in step with `SensorInput`.
- Root `*.ply` / `*_out.pbscan` files are generated outputs.
- There is no `regression` skill in this repo or the workspace (checked 2026-11-14). The regression check is `bench_slam` on both recordings plus the integration test, as described below.

## Simulator (`simulator/`)
- `msim` is a MuJoCo Mid360 + IMU simulator (uv project, Python 3.13) that serves the msensor gRPC protocol like `playback_publisher` (`sensors.LidarService/getLidarScan`, `sensors.ImuService/getImuData`, default port 50051), so mslam connects to it through `remote_scanner`. Scenes are box floor plans in YAML (`scenes/`, format at the top of `src/msim/scene.py`); the sensor is flown with the keyboard in the MuJoCo viewer or follows a scripted trajectory (`trajectories/`). User docs: `simulator/readme.md`.
- It runs and is tested on the macOS host only, never in the dev container: `cd simulator && uv sync && uv run pytest` (87 tests, about 25 s, including an end-to-end gRPC test). The gRPC stubs are generated from `third_party/msensor/proto` on first use and are not checked in.
- Headless, deterministic: `uv run msim serve --scene scenes/two_rooms.yaml --headless --trajectory trajectories/two_rooms_loop.yaml --unpaced --gt-log gt.csv --exit-when-done`; `uv run msim check localhost:50051` audits rates, timestamps and sequence gaps. The viewer needs `uv run mjpython -m msim serve --scene ...` on macOS; if `libpython3.13.dylib` is not found (uv's standalone Python), symlink it into `.venv/lib/` (path in the error). `serve` prints the command line and every option at startup, marking defaults. From the dev container mslam reaches it at `host.docker.internal:50051`.
- Emulated conventions, taken from the msensor/mslam sources and the recordings: one ns clock; 9600 points per scan 5 us apart, header = first point, a scan every 48 ms; IMU 200 Hz with a 1.3 ms phase offset; accel is specific force `R^T (a - g)` in g, gyro rad/s, sensor frame = IMU frame (no lever arm); every point cast from the pose at its own time and expressed in that sensor frame (needs deskewing); misses are `(0,0,0)` with intensity 0 (point count kept). Paced runs drop the oldest samples like the real server; `--unpaced` blocks instead (lossless, reproducible, not real behaviour).
- Scan pattern (`--pattern`, `src/msim/pattern.py`): `measured` (default) replays the directions measured on `test/data/living_room_garden.pbscan` (4 beams, about 181 rev/s in azimuth, elevation nodding -7..52 deg with a ~102 ms period not locked to the scans, so each scan sees a different elevation band). Its table `simulator/out/mid360_pattern.npz` (87 MB, git-ignored) is built from the recording on first use, so it needs Git LFS pulled; without it `serve` stops with an error rather than falling back. `rosette` is the old synthetic pattern (full field of view every scan, unrealistic); a file path takes a `msim gen-pattern` `.npz` or a `.npy` table. Simulated scan k uses recorded scan k, cycling.
- Intensity (`src/msim/reflectivity.py`): Livox calibrated reflectivity, `150 * reflectance * cos(incidence)` (0..150) or `151 + 104 * cos` for retro-reflectors; detection range `40 m * (s / 0.1)^0.269` from the datasheet's 40 m at 10 % / 70 m at 80 %. Per-kind defaults (wall 0.4, floor 0.2, ceiling 0.45, obstacle 0.3) are calibrated so `two_rooms_loop` matches the median intensity of `living_room_garden` (49 vs 48); `min_intensity: 50` then drops about half the points, as on real data.
- Viewer keys avoid WASD: MuJoCo binds every letter to a display toggle, and S, W, R, L, K, G cannot be restored from Python (the other `opt.flags` are restored every frame). Motion keys: arrows (forward/back, yaw), Z/X strafe, E/Q up/down, Y/H pitch, U/O roll, N (hold) level, B level/body translation mode, Space brake, Enter reset. Full 3D attitude (rotation matrix, no pitch limit); the gyro is the same body rate that integrates the attitude. MuJoCo forwards presses and repeats but not releases, so held-key detection is a timeout (0.45 s / 0.18 s). The keys are unit-tested but have not all been driven by hand.
- Ground truth: `--gt-log` writes one row per scan at its last point time (where mslam registers it), R = Rz Ry Rx; `msim compare gt.csv est.csv` (est = `bench_slam --trajectory`) handles mslam's Rx Ry Rz Euler angles and matches on timestamp + 47.995 ms. `--record x.pbscan` writes an msensor recording for `bench_slam`.
- Verified: a `--record`ed `two_rooms` run (829 scans, noise-free) through `bench_slam` with the integration config: position error mean 16.3 mm, max 27.3 mm, rotation mean 0.41 mrad, all scans on the IMU path (measured before the measured pattern and the reflectivity model). The owner has run live mslam against it over gRPC with the viewer. Not re-measured with the measured pattern; no noise model is calibrated against the real IMU.

## Estimator conventions and pitfalls
- Time: a scan is registered at its last point's time, IMU samples are paired with scans by timestamp and never by arrival, and the IMU clock in `Slam` is not reset on the IMU path of `Update` (see "Time convention" in `docs/arch.md`). Before these three held, the first-round correction on `living_room_garden` was 12.8 mm / 1.60 mrad.
- Never bind `.linear()`, `.translation()` or any block of a temporary Eigen transform with `auto` (`auto R = toAffine(...).linear();`): the block dangles. Under GCC 16 one such line in `ImuMath.cc` made 7 unit tests fail. Copy into `Eigen::Matrix3d` / `Eigen::Vector3d`.
- The registrations optimize the pose itself on a moptim manifold (`SE3Manifold`: 12 doubles `[R | t]` column-major, tangent `[rho, omega]`, `plus(T, d) = se3Exp(d) * T`, a LEFT increment). The IMU registration uses a `ProductManifold` of it and `Euclidean(18)` (state `[pose_j | v_j bg_j ba_j | v_i bg_i ba_i]`, ambient 30, tangent 24). A model's `jacobian` is the derivative with respect to the step at zero; a right-increment Jacobian is silently wrong. An optimizer and all its costs must be built from the same manifold object (the `addCost` assert is compiled out in Release). `Point3PlaneDistance` / `Point3Distance` take the pose `T` as state and apply `T * source_pose^-1` to inputs that `IcpWorkspace` already moved by the pose of the current round, so each model is built per round with that `source_pose`. `Point3PlaneDistance` has a scalar residual `n·(q − T·p)`. The IMU preintegration factor has an analytical jacobian (`ImuPreintegrationFactor::jacobian()`, used through `moptim::AnalyticalCost`; the numerical `NumericalCostCentral` is only the test reference), and its residual reads the state directly (no log/exp round trip).
- Registration always runs `reg_iterations` × `optimizer_iterations`: the early exit ends the ICP loop after four rounds that each moved the pose by less than 0.1 mm and 0.1 mrad (`isNegligibleRoundStep`, `IcpWorkspace.cc`), so it cannot fire with three rounds. (1 µm was tried first: loop-closure verification then ran 11.4 of its 20 rounds on average and the back end took 1.8 s on `living_room_garden`; 0.1 mm gives 1.46 s with the same accepted loops, RMS and matched fractions.) Before it the loop counted rounds whose optimizer returned `SMALL_DELTA`, which only means that round's own solve converged (its last tiny step was rejected on a rounding-level cost increase): with some roundings point-to-point ICP stopped after five of 30 rounds while still moving millimetres per round (`PointToPointRecovery` failed). It matters for `register_scans`, loop-closure verification (20 rounds) and the tests, not for the SLAM front end.
- `VoxelHashMap` searches `map.search_radius` rings of voxels around the query (optional, default 1, range 0 to 8, set in `main.cc`, `bench_slam` and the tests from the config), so the true nearest neighbour is only guaranteed within `search_radius * map.resolution` (0.1 m by default), while `max_correspondence_distance` is 0.3 in the test config. Lowering the gate to 0.1 breaks `living_room_garden` (measured before the timing fixes). Measured 2026-11-16, `bench_slam` on `living_room_garden` with the integration config: radius 2 gives pose `0.043182777 -0.000063221 0.001170334 -0.003363126 0.002206562 0.487423511` (0.49 mm from radius 1), first round 9.103 mm / 0.679 mrad, register about 2.23 s against 1.57 s.
- The first 10 scans only seed the map (`SlamPipeline::kInitScans`); they are range-filtered but neither downsampled, deskewed nor transformed by the pose.
- Preintegration covariance (fixed 2026-11-17): the per-sample noise is `Q(dv) = na²·dt`, `Q(dp) = ¼·na²·dt³` and `Q(dv,dp) = ½·na²·dt²` (a numpy Monte Carlo of the same recursion matches it within 0.35%; test `ImuPreintegrator.CovarianceOfStaticAccelNoiseMatchesContinuousModel`). The old `Q(dp) = na²·dt` without the cross term made the position variance about 1300 times too large. Correcting it alone with `kImuWeight` 0.01 moved `living_room_garden` to 0.98 m from the origin: the white-noise covariance is overconfident for the real IMU error (sample timing, no lever arm, bias drift). Swept with `bench_slam`: 0.003, 0.001, 0.0003 and 0.0001 all pass the gate (0.043 to 0.044 m); below about 0.0003 the first-round correction reaches the dead-reckoning level (21 mm), so the factor no longer helps. 0.003 was kept; where the failure starts between 0.003 and 0.01 was not measured.

## Known open issues (found 2026-11-14, not fixed)
Performance, as shares of a gprof run on `living_room_garden` taken before the timing fixes (the pipeline was single-threaded then; the two searches below run in parallel on oneTBB when `num_threads` != 1, see "Threads" above):
- 5-nearest search plus eigen-solve for surface normals, about 35%: normals are recomputed every scan although map voxels saturate; they could be kept in the map and invalidated on insertion (still open; it composes with the parallel estimation).
- 1-nearest correspondence search, about 26%: per-point work on a read-only map; runs in parallel on oneTBB when `num_threads` != 1 (default 1).
- IMU factor numerical Jacobian, about 11% (measured before the manifold change). Fixed: the factor has an analytical jacobian. `se3Log` (`SE3.hh`) also calls `Transform::rotation()`, which runs an SVD, where `.linear()` would do; `ImuRegistration` now calls it once per `Align` (first-round correction) and the IMU factor no longer calls it.
- Deskew, about 10%: it rotates all 9600 points although about 11% survive the filters.

Estimator:
- Registration stops before converging: before the timing fixes the third round still moved the pose by 2 to 4 mm on average, and 8 rounds were needed to reach 0.4 mm. After the fixes, 2 rounds give the same final pose as 3 within about 1 mm on both recordings and are about 17% faster. One round, or one optimizer iteration per round, broke `living_room_garden` before the fixes; not re-measured since.
- Tilted start (read from the code, untested; both recordings start level): init scans go into the map in the raw sensor frame while the state takes roll and pitch from a single accelerometer sample.
- `SlamState` stores Euler angles (singular at ±90° pitch) and converts to and from a rotation matrix on every IMU sample.
- A scan is inserted into the map even when registration found no correspondences. There is no robust loss and no planarity check on the normals.
- LiDAR residuals have unit weight, the IMU factor is scaled by a hard-coded 0.003 (`kImuWeight`, see "Preintegration covariance" above), and the IMU noise parameters are not in the config.
- The pose is published per IMU sample although samples are processed in a burst per scan, and `SlamServer::map_history_` grows without bound (`StreamMap` offsets are indexes into it, so any bounding or compaction must keep the epoch/offset contract: bump the epoch or keep offsets absolute).
- Not verified anywhere: a live sensor run, the `pi5` preset, the streaming RPCs (`GetTransformedScan`; `StreamMap` and `GetMap` are covered by `test_slam_server` with a real stub, `GetMapIncrements` is not), and the 50 ms IMU wait with an absent IMU stream outside unit tests.

## Repo layout gotchas
- mslam targets are compiled with `MSENSOR_NO_LEGACY_NAMES` (set in the top-level `CMakeLists.txt` after the msensor subdirectory), so use the namespaced `msensor::` names; the legacy global aliases are not available.
- `third_party/` are submodules (`moptim` optimizer, `msensor` sensors/recorder, `robin-map`); `msensor` is maintained in-house (its recording/playback and gRPC code is fair game), `moptim`/`robin-map` are external. Submodules show as modified in git status.
- `SlamServer` map RPCs: `StreamMap` is the cursor-based stream (contract in `grpc/slam.proto` and the readme: `(epoch, offset)`, first message an empty epoch chunk, reset announced at once). `GetMap` / `GetMapIncrements` are deprecated but unchanged. Each `StreamMap` handler copies at most 1024 chunk pointers out of `map_history_` per `map_increment_mutex_` acquisition and never holds it while concatenating or writing; keep the SLAM-thread calls (`updateMapIncrement`, `reset`, ...) O(1). `reset()` bumps `map_epoch_` (non-zero, randomly seeded per process). Its tests build a real server on a unix socket (`RunningServer` in `test_slam_server.cc`).
- `SlamServer::GetStatus` (unary, `SlamStatus` in `grpc/slam.proto`) reports the SLAM server's link to its sensor server: `SensorLink` UNKNOWN (no source attached), NOT_APPLICABLE (`remote_scanner` is `local`), DISCONNECTED, CONNECTED_IDLE, STREAMING, plus the sensor address and the age in ms of the last scan and IMU sample (-1 = none yet). `src/main.cc` attaches a `RemoteSensorStatus` (over `msensor::SensorsRemoteClient::linkUp()` / `lastScanAge()` / `lastImuAge()`) or a `LocalSensorStatus` with `SlamServer::setSensorStatus` (a `shared_ptr`, so a request in flight never outlives it; detached before `main` returns). `classifySensorLink()` (`include/mslam/slam/SensorStatus.hh`): not connected is DISCONNECTED; connected with both streams' last sample at most `kSensorStreamingMaxAge` (2 s) old is STREAMING; any other connected state is CONNECTED_IDLE (a paused `playback_publisher` is connected and silent, so it is idle, not disconnected). The log line in `main.cc` used to say "Connected to remote sensor server" right after `start()`, before any connection existed (gRPC connects lazily and retries every second); it now says "Connecting". Tests: `SlamServerTest.Status*`, `SensorLinkClassification.*`, `SlamServerStatus.IsServedOverTheWire`; the viewer side is `client/sensor_status.py` and `client/tests/test_sensor_status.py`.
- `client/` is a Python viewer (uv, `proto_gen/` generated from `grpc/slam.proto`; after a `.proto` change regenerate only `slam_pb2*` with the command in `client/README.md`, passing just `../grpc/slam.proto`, so the unrelated stubs do not change); `viewer/` is a TypeScript browser PLY viewer (`npm run dev`; run `npm ci`, `npm run build` and `npm test` in the devcontainer, since `node_modules/` is installed for Linux; tests are vitest `src/*.test.ts`, node environment).
- Docker builds: `deployment/Dockerfile` (SLAM), `deployment/DockerfileViewer`. The `pi5` preset is GCC (`MSLAM_CPU` `cortex-a76`, `MSLAM_WITH_TBB` ON) and the runtime stage installs `libtbb12` (the install rule skips `/usr/lib`, so the runtime package is needed). The Docker image itself and a run on a Pi 5 are not verified.
